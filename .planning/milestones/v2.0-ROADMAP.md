### Phase 5: Full Agent Suite & Parallel Fan-Out

**Goal**: The four remaining specialist agents exist and, together with FundamentalAnalysis, run in a true parallel fan-out; the Synthesis fan-in waits on all dispatched agents and degrades gracefully to a PARTIAL memo when any agent fails.
**Depends on**: Phase 4 (v1.0 Minimal Agent Run)
**Requirements**: AGENT-01, AGENT-02, AGENT-03, AGENT-04, AGENT-05, AGENT-06, EXEC-04
**Success Criteria** (what must be TRUE):

  1. A single research run dispatches all applicable agents (FundamentalAnalysis, SentimentNLP, RiskAssessment, MacroSector, ComparableCompanies) concurrently rather than sequentially.
  2. Each of the four new agents produces a cited narrative from its designated sources (news/arXiv for sentiment, risk, FRED macro/sector, comparables).
  3. The Synthesis fan-in waits for every dispatched agent to finish before computing memo status.
  4. When one or more agents fail, the memo still generates as PARTIAL with the failed/missing sections explicitly marked with a reason (never silently omitted).

### Phase 12: Observability & Offline Eval

**Goal**: Every agent call is traced in LangSmith, per-agent costs aggregate to a per-memo total shown on the memo, and an offline RAGAS eval job scores retrieval quality on a schedule.
**Depends on**: Phase 5 (the full agent suite is the surface being traced and cost-tracked)
**Requirements**: OBS-01, OBS-02, OBS-03, MEMO-06
**Success Criteria** (what must be TRUE):

  1. Every agent call emits a LangSmith trace.
  2. Per-agent cost is captured and aggregated into a per-memo total.
  3. The memo displays its total generation cost (LLM tokens + external API call counts).
  4. An offline RAGAS evaluation runs as a scheduled Celery beat job and produces retrieval-quality scores.

**Plans**: 14/14 plans complete

### Phase 999.2: ComparableCompanies peer selection is poor for mega-caps (BACKLOG)

**Goal:** [Captured for future planning]
**Requirements:** TBD
**Plans:** 0 plans

Flagged during Phase 6 live verification (2026-07-06). `comparable_companies.py` sources peers from yfinance's industry-key `top_companies` list (D-05). For a mega-cap that dominates a narrow industry bucket (e.g. AAPL at 99.96% market weight in yfinance's "consumer-electronics" industry), the remaining `top_companies` entries are tiny, unrelated tickers (SONO, TBCH, AXIL, FXHO, WTO) instead of real competitors (MSFT, GOOGL, META, AMZN — all classified under different yfinance industries). Confirmed live against the real yfinance API — not a bug, a real limitation of the industry-key approach. Revisit with market-cap-tier matching or a curated override list for large caps in a future phase.

### Phase 999.3: Stray "Event loop is closed" tracebacks not attached to any agent failure (BACKLOG)

**Goal:** [Captured for future planning]
**Requirements:** TBD
**Plans:** 0 plans

Flagged during Phase 6 live verification (2026-07-06). After fixing the httpx-client-singleton event-loop bug (reset_news_client/reset_arxiv_client/reset_edgar_client/reset_groq_client, wired into run_research_task), 2 stray `RuntimeError: Event loop is closed` tracebacks still appeared in worker logs across several live runs — but neither was attached to any of that run's actual FAILED agent tasks (all real failures in those runs had clean, complete `groq.RateLimitError` tracebacks with no event-loop error in them). Likely garbage-collection noise from a previous run's now-orphaned httpx client object being finalized at an unpredictable later moment — cosmetic, not functional. Confirmed 0 occurrences under normal single-run conditions. Revisit if it recurs with more live testing once the Groq daily quota resets.
